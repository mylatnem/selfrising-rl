## 总览：九个阶段，每阶段有验收关卡

做工程最容易犯的错不是"写错代码"，而是**顺序错了**：先训练，再发现环境有 bug；先部署，再发现奖励设计有问题。

所以全程只做一件事：**每个阶段结束时，用一条可执行的命令证明这一阶段是对的，才允许进入下一阶段。**

| 阶段 | 产出 | 验收关卡（Gate） |
|---|---|---|
| 0 | 一句可测量的目标 | 能说出"什么算完成" |
| 1 | 能加载的物理模型 | `nq/nv/nu/timestep` 打印且符合预期 |
| 2 | 能 `step()` 的 Gym 环境 | 随机动作 50 步不发散 |
| 3 | 自检脚本 | 五项全 `[ OK ]` |
| 4 | 对照组基线 | 脚本策略成功率 ≥ 90% |
| 5 | 训练好的策略 | 评测成功率 ≥ 90% |
| 6 | 定位过 3 个真实 bug | 能自己判断"是代码、物理还是奖励错了" |
| 7 | 压力阶梯表 | 知道它在哪一档会垮 |
| 8 | 可编译的固件 | `pio run` 通过 |

**卡在某一关就不要往下走。** 90% 的返工都来自"先跑起来再说"。

## 阶段 0 · 先定"完成"的定义

在写第一行代码之前，先把目标写成**可以用命令验证**的句子。

❌ "用强化学习让机器人站起来"
✅ "四个跌倒姿态，各 10 回合（初始角扰动 ±15°），成功率 ≥ 90%，平均起立时间 ≤ 3 秒"

为什么要这么具体：

- 它决定**观测要包含什么**（要判断姿态，就需要姿态量）
- 它决定**奖励怎么设计**（要"站起来"，就需要直立度）
- 它决定**成功怎么判**（"站起来"= 倾角小 + 保持住 + 别乱晃）
- 它决定**什么时候算做完**（不然你会无限调参）

本工程的最终定义（实现在 `selfrising/reward.py` 的 `RewardConfig`）：

| 条件 | 阈值 | 为什么是这个值 |
|---|---|---|
| 倾角 | ≤ 14.32° | 对应 `upright = 0.95`（cos(14.32°)=0.969，留了余量） |
| 关节角 | ≤ 0.12 rad | 目标姿态是两个关节归零，允许一点稳态误差 |
| 基座速度 | ≤ 0.25 m/s | 排除"路过直立位置"的假成功 |
| 保持 | 1 秒 | 排除"冲上去又倒" |
| 超时 | 14 秒 | 起不来就该结束，不然白烧算力 |

**关卡 0**：你能把上面这张表默写出来。写不出来说明目标没定清楚。

## 阶段 1 · 建立最小可运行世界

### 1.1 模型从哪来

三种选择，按成本排序：

| 方案 | 成本 | 后果 |
|---|---|---|
| 用别人的 MJCF | 最低 | 结构和参数是黑盒，出问题难查 |
| 自己写简单盒体 | 低 | 物理可信，但和实物不像，学了不能上板 |
| 3D 建模 + 导出 MJCF | 高 | 最真实，但要多学一个工具链 |

**本工程选第一种**（`assets/robo1.xml` 来自原作者发布物），但做了两件事补偿：

1. 逐字读一遍模型，把每个数值的含义搞清楚（手册第 3 章）
2. 把 `meshdir` 改成自己的目录，确认 mesh 都能加载

> 如果你是第一次做，建议先用第二种（两个盒子 + 一个铰链）跑通全流程，再换成真实模型。**先求通，再求真。**

### 1.2 读模型时必查的六项

打开 MJCF，逐项确认（缺一项后面就会踩坑）：

| 查什么 | 在哪看 | 期望 | 不对会怎样 |
|---|---|---|---|
| 自由度 | `nq` / `nv` / `nu` | 9 / 8 / 2 | 观测维度和动作维度按它算 |
| 物理步长 | `<option timestep>` | 0.001 | 改大了接触会抖，改小了慢 |
| 积分器 | `<option integrator>` | `implicitfast` | 默认 Euler 在刚性接触下会炸 |
| 自由关节 | `<joint type="free"/>` | 在根 body 上 | 没有就无法整体运动 |
| 关节限位 | `<joint range>` + `forcerange` | ±1.57 | 策略会输出超出物理范围的目标 |
| 碰撞体 | `<geom contype/conaffinity>` | 至少有一组互相碰撞 | 机器会穿地（本项目就踩过，见 6.3） |

### 1.3 三条命令验证模型

```bash
python -c "import mujoco; m=mujoco.MjModel.from_xml_path('assets/robo1.xml'); print(m.nq,m.nv,m.nu,m.opt.timestep)"
python -c "import mujoco; m=mujoco.MjModel.from_xml_path('assets/robo1.xml'); print([mujoco.mj_id2name(m,mujoco.mjtObj.mjOBJ_BODY,i) for i in range(m.nbody)])"
python -c "import mujoco,numpy as np; m=mujoco.MjModel.from_xml_path('assets/robo1.xml'); d=mujoco.MjData(m); mujoco.mj_forward(m,d); print(d.qpos)"
```

**关卡 1**：`9 8 2 0.001` + body 列表里有 `foot/ATOM/arm1/arm2` + `qpos` 全是 0 且 `qpos[3:7]` 是四元数 `(1,0,0,0)`。

### 1.4 关于坐标系的第一个陷阱

模型的根 body `foot` 有一个**坐标系原点**，它和"机器人所在的位置"不是一回事。本工程里原点在几何体外面，各部件相对它偏 8～19 cm。

记住这一点，阶段 6 的第二个坑就是它。

## 阶段 2 · 写环境（MDP 四件套）

### 2.1 顺序很重要

按这个顺序写，每一步都能单独验证：

```
动作空间 → 观测 → 终止条件 → 奖励
```

反过来（先写奖励）会让你在错误的动作空间上设计奖励，全部推倒。

### 2.2 动作：先决定"策略能输出什么"

| 方案 | 优点 | 缺点 |
|---|---|---|
| 力矩 | 最接近物理 | 难训、难部署、真机要力矩传感器 |
| 绝对角度 | 直观 | 一步到位易撞限位，探索空间大 |
| **增量角度**（本工程） | 有界、平滑、易迁移 | 需要多步才到位 |

本工程：`目标 = 旧目标 + 0.08 × 动作`，再限幅到 ±1.55 rad（`ACTION_DELTA` / `ACTION_LIMIT`）。

这两个数字**必须和固件里的一模一样**，否则训练出来在板子上就是"合法地乱动"。

### 2.3 观测：每一维都要能回答"为什么在"

本工程 10 维：

| 维度 | 内容 | 为什么需要 |
|---|---|---|
| 0-2 | 重力在机体系的分量 | 姿态，连续、无万向节死锁、IMU 直接可测 |
| 3-4 | 两关节角 | 知道手臂在哪 |
| 5-6 | 两关节角速度 | 判断"还在动还是停了" |
| 7-8 | 上一帧目标角 | 舵机是位置控制，需要记忆 |
| 9 | 基座高度 | 常量即可（真机没高度传感器） |

> 为什么不用 roll/pitch：接近垂直时连续，但侧倒 90° 附近会跳变，还有万向节死锁。用重力向量规避了这两个问题。

### 2.4 终止条件：三条路，缺一不可

```python
terminated = 成功 or 失败
truncated  = 超时 and not terminated
```

**失败判定的设计最容易出错**（本工程改过两次）。原则：**只用有物理意义的量**。

| 写法 | 结果 |
|---|---|
| ❌ `qpos[2] < -0.05` | `qpos[2]` 是坐标系原点，站直时会掉到 -0.05，把正常回合误判成失败 |
| ✅ `连续 0.5 s 接触点数为 0` | 真的被弹飞/穿模才成立 |

### 2.5 奖励：每一项都要能回答"策略怎么作弊"

设计每一项时问三个问题：

1. 这项在鼓励什么行为？
2. 策略能怎么白拿这一项？
3. 去掉它，学出来的动作会变成什么样？

本工程踩过的最大坑就在这里（见 6.3）：一个**没有物理意义**的高度惩罚项，让"站起来"每步倒扣 0.85 分，策略于是学会了"躺着别动"。**它不是学不会，是它在理性地最大化我给的奖励。**

**关卡 2**：`env.reset()` 后能打印 obs 形状 `(10,)`，随机动作跑 50 步奖励不发散、数值不出 `nan`。

## 阶段 3 · 先写自检，再谈训练

**训练会掩盖环境 bug。** 一个坏掉的环境照样能跑出"看起来很合理"的曲线，让你在错误的方向上调三天超参。

所以在训练之前，写一个 `selftest`，把前置条件全部检查一遍：

| 检查 | 不通过说明 |
|---|---|
| 依赖版本 | 没装/装错环境 |
| 模型加载 | mesh 缺失、XML 改坏 |
| 环境构建 | obs/act 形状、控制频率对不上 |
| 随机步进 | 控制限幅、积分器、碰撞参数有问题 |
| 参考动作回放 | 参考数据与模型不匹配 |

本工程的 `scripts/selftest.py` 就是按这五项写的。

**关卡 3**：五项全 `[ OK ]`。任何一项 `[FAIL]` 都先修它，不要往下走。

## 阶段 4 · 做基线，否则没有对照

没有基线，你永远不知道"训练出来的 78% 是好还是坏"。

本工程的基线：用参考动作（keyframes）开环回放。

```bash
python -m scripts.run_scripted --episodes 5
```

**关卡 4**：脚本基线在标称姿态上成功率 100%，平均用时 2.2～2.9 秒。

如果基线不到 90%，**先别训练**——说明环境或参考动作有问题。RL 不能修环境 bug，只会把它学进去。

> 这里有个反直觉的地方：基线 100% 看起来像"任务已经被解决了"。但基线是开环的，扰动一大就垮；RL 要学的是**闭反馈**。所以正确的说法是"基线在标称条件下是专家示范"，不是"任务太简单"。

## 阶段 5 · 训练

### 5.1 配置从"快"的开始

```bash
python -m scripts.train_ppo --config configs/ppo_fast.json      # 30 万步, 12 分钟
```

先跑快的，是为了**尽快走完"训练→看曲线→发现问题"的一轮**。直接上 150 万步，发现问题时你已经浪费了一小时。

### 5.2 训练时只看三个指标

| 指标 | 健康形态 | 异常说明 |
|---|---|---|
| `rollout/ep_rew_mean` | 持续上升 | 见顶后倒退 = 奖励被套利 / 熵塌缩 |
| `rollout/ep_len_mean` | **从上限开始下降** | 一直贴着上限 = 从未成功，也没失败 |
| `rollout/success_rate` | 从 0 出现非零 | 一直 0 = 成功条件不可达 |

**`ep_len_mean` 是最诚实的指标**：回合提前结束，只可能是因为成功了（或崩了）。本工程第一次成功时，它是从 701 掉到 481 的。

### 5.3 一个必须知道的陷阱

`ep_rew_mean` 会**因为回合变短而下降**。本工程从 994 掉到 772，看起来是退步，实际是每步奖励从 1.36 涨到 1.63。

**永远换算成"每步奖励"再比较。**

**关卡 5**：评测成功率 ≥ 90%。

## 阶段 6 · 诊断：三类 bug，三种查法

这一章是全文最重要的部分。**做工程 80% 的时间在查错，而不是写新代码。**

先记一个判断框架：

| 症状 | 第一嫌疑 | 验证手段 |
|---|---|---|
| 程序报错 | 代码 | traceback |
| 不报错但物理怪（穿地、飞走、卡住） | 模型/物理参数 | 打印 `qpos`、`ncon`、`contact.dist` |
| 能跑但学不会 | 奖励/终止条件 | 打印每一项奖励的数值 |
| 学得会但结果不对 | 成功判定 | 手算一条轨迹的四个条件 |

### 6.1 案例一：程序在 `reset()` 就崩

```
IndexError: too many indices for array: array is 1-dimensional, but 2 were indexed
```

定位过程：`selftest` 吞掉了 traceback，直接跑 `SelfRisingEnv()` 拿到行号，发现是

```python
self.data.ctrl[self.idx.actuator_ids] = 0.0    # actuator_ids 是元组 (0, 1)
```

**NumPy 把元组下标解释成多维下标**：`arr[(0,1)]` == `arr[0,1]`。改成 `list(...)` 才对。

教训：**下标是元组还是列表，在 NumPy 里语义完全不同。**

### 6.2 案例二：回合 0.2 秒就结束

现象：脚本基线四个姿态全部 0.2～0.7 秒结束，末态倾角有的还是 11°（快站直了）。

查法：打印每一步的 `h`（`qpos[2]`）、`ncon`、`|qvel|`：

```
t=0.02 h=0.125   t=0.32 h=0.070   t=0.64 h=-0.051  ← 触发 h < -0.05
```

看起来像"沉进地面"，但空放 200 步（不控舵机）时 `h` 稳定在 0.125、`ncon=4`，根本不掉。

结论：**`qpos[2]` 不是高度**，它是根 body 坐标系原点的 z，原点在几何体外面，站直过程中会掉到 0 以下。

修复：失败判定改成"连续 0.5 s 无接触点"。

教训：**用一个量之前，先确认它的物理含义。** 名字叫 height 不代表它是高度。

### 6.3 案例三：能站起来，但成功率永远是 0

现象：`ep_len_mean` 死贴 701（从不终止），回报从 -508 爬到 -28 后**倒退**到 -173。

第一轮诊断：把每一项奖励打印出来，发现高度项

```python
-height_scale * (height - 0.08)**2 * w_height   # 50 * (h-0.08)^2
```

在站直（`h = -0.05`）时等于 **-0.85/步**，而站直奖励只有 +1.0。**站起来倒扣分，躺着才不扣。**

修复一：删掉这个没有物理意义的高度项。回报立刻从 -173 变成 +684（平台期）。

第二轮诊断：684 ÷ 701 ≈ 0.97/步，而"站直+关节归位"应该是 1.75/步。说明关节分一分没拿。打印轨迹：

```
t=2.02  tilt=0.2  q=[1.57 -1.55]  |v|=0.00
```

**站得完美，但两个关节顶死在机械限位上。**

修复二：`joint_goal` 奖励原本是高斯形状 `exp(-Σq²/2σ²)`，在 1.57 rad 处等于 `exp(-38.9) ≈ 0`——**梯度为零**，策略根本不知道"转回 0 有奖励"。改成线性斜坡：

```python
closeness = 1 - Σq² / (2·limit²)
```

改完后：成功率 0 → 55%（训练采样），评测 100%。

教训：**奖励的形状比权重更重要。** 权重再大，梯度为 0 也传不回去。

### 6.4 诊断的通用动作顺序

1. **先看指标，不看代码**：哪个指标不对？什么时候开始不对？
2. **打印物理量**，不要靠猜：`qpos`、`qvel`、`ncon`、每一项奖励
3. **对照一条完整轨迹**，找出"从哪一步开始偏离预期"
4. **分清三类**：代码错 / 物理参数错 / 奖励设计错
5. 修复后**只改一个变量**，重跑

**关卡 6**：给你一条异常曲线，你能说出"该打印什么"。

## 阶段 7 · 评测与压力阶梯

### 7.1 `eval` 和 `rollout` 不是一回事

| | rollout（训练中） | eval（单独评测） |
|---|---|---|
| 动作 | 带探索噪声 | 确定性（argmax） |
| 用途 | 判断学习趋势 | 判断真实能力 |

本工程出现过"训练里 55%、评测 100%"——**差的全是探索噪声**。看错这个会以为策略没学会。

### 7.2 压力阶梯：一次只加一个真机扰动

```bash
bash tools/eval_ladder.sh
```

| 档 | 扰动 | 本工程结果 |
|---|---|---|
| ① | ±15° 初始角 | 100% |
| ② | +1 步动作延迟 | 100% |
| ③ | +观测噪声 | 100% |
| ④ | +域随机化 | 95% |
| ⑤ | 全叠加 | 95% |

结论怎么读：

- **②③ 不掉** → 策略是闭反馈的，不靠精确时序
- **④ 掉** → 某些物理参数组合下能力不足，这才是 sim2real 的真实缺口

**关卡 7**：能说出"它在第几档开始掉、掉在哪个姿态"。

## 阶段 8 · 导出与部署

### 8.1 权重 → C 数组

```bash
python firmware/tools/export_policy.py runs/ppo_fast/final_model.zip -o firmware/include/policy.h
```

成功会打印网络形状和 `max|w|`。

### 8.2 上板前必须对齐的四件事

| 项 | 仿真 | 固件常量 |
|---|---|---|
| 控制频率 | 50 Hz | `CTRL_HZ` |
| 动作缩放 | 0.08 rad/步 | `ACTION_DELTA` |
| 动作限幅 | ±1.55 rad | `ACTION_LIMIT` |
| 观测维度 | 10 | `OBS_DIM` |

**这四项不一致，策略在板子上就是"合法地乱动"。**

### 8.3 分两步上电

1. `DRY_RUN=1`：只打印观测，**不动舵机**。确认站直时重力向量 ≈ `(0,0,-1)`
2. `DRY_RUN=0`：真动。先用手扶着，确认方向对

**关卡 8**：`pio run` 编译通过，且串口的观测符号与仿真一致。

## 最后一句
