# 第一部分 · 建立认知

## 第 1 章 这个工程在解决什么问题

### 1.1 一句话

**让一个被推倒的两自由度不倒翁，用两个小舵机自己站起来。**

具体一点：机器人以四种姿态倒在地上（向左右倒、向前后倒各一种），策略要在 3 秒内把它扶正，并稳稳站住 1 秒。

### 1.2 为什么不直接写控制程序

你完全可以用 if-else 写一个"站起来"的脚本，事实上这个工程里就有（第 12 章的基线）。但脚本有三个死穴：

| 问题 | 后果 |
|---|---|
| 只对特定初始姿态有效 | 被推倒的角度稍变就失败 |
| 参数靠人调 | 换个机器人要重调一遍 |
| 无法处理反馈 | 不知道"现在倒了多少度"，只能盲推 |

强化学习学的是**反馈策略**：看当前状态，决定往哪推、推多快。这就是"闭环"。

### 1.3 成品指标（本工程实测）

| 指标 | 数值 | 怎么测的 |
|---|---|---|
| 标称成功率（±15° 扰动，确定性动作） | **100%** | `eval_final.json` |
| 平均起立时间 | **2.6～2.8 秒** | 同上 |
| 训练中采样成功率 | 55% | TensorBoard `rollout/success_rate`（差异来自探索噪声） |
| 压力阶梯（延迟/噪声） | 100% | `tools/eval_ladder.sh` |
| 压力阶梯（+域随机化） | 95% | 同上 |
| 训练成本 | 30 万步 / 12 分钟 / 纯 CPU | — |

## 第 3 章 强化学习的最小直觉

### 3.1 三句话

1. **试错**：策略随便动一下
2. **打分**：环境告诉你这一步做得怎么样
3. **记住**：把"这种情况下这么做得分高"记下来

循环几千次，策略就变好了。

### 3.2 与其它方法的区别

| | 监督学习 | 传统控制（PID） | 强化学习 |
|---|---|---|---|
| 需要什么 | 标注好的"正确答案" | 数学模型 + 手调参数 | 只要能打分 |
| 学什么 | 输入→输出的映射 | 误差→修正量 | 状态→动作的策略 |
| 难点 | 数据标注 | 参数难调、非线性难处理 | 奖励设计、训练不稳 |

本工程用 RL 的原因：**"怎么用两个舵机把自己撬起来"这件事，人手写规则写不出来，但"站直了给分"很容易定义。**

### 3.3 为什么在仿真里做

| 优势 | 具体 |
|---|---|
| 便宜 | 摔坏一百次也不花钱 |
| 安全 | 不会伤人 |
| 快 | 1 秒真实时间可以跑几十秒仿真 |
| 可复现 | 固定随机种子，结果完全一致 |
| 能并行 | 8 个环境同时跑，数据采集快 8 倍 |

代价是：仿真和现实永远有差距（**sim2real gap**），所以第 15 章要专门做压力测试。

# 第二部分 · 地基：模型与物理

## 第 5 章 MuJoCo 是什么

### 5.1 它算什么

MuJoCo 做两件事：

1. **刚体动力学**：给定质量、惯量、关节、力矩，算出下一秒的位置和速度
2. **接触求解**：算出两个物体互相顶着时，各自受多大力

它不解渲染、不做动画、不懂游戏逻辑。**它只是一个"物理计算器"。**

### 5.2 为什么不用游戏引擎（Unity / 物理引擎 PhysX）

| | MuJoCo | 游戏引擎 |
|---|---|---|
| 目标 | 物理准确 | 实时好看 |
| 接触 | 精确、可调 | 近似、常穿模 |
| 可复现 | 是 | 难 |
| 机器人建模 | MJCF 原生 | 要插件 |
| 速度 | 快 | 更慢 |

机器人领域常用的三个：MuJoCo（轻量、CPU 友好）、Isaac Sim（GPU、生态大、吃显卡）、PyBullet（免费但接触质量差）。

### 5.3 MJCF 与 URDF 的关系

| 格式 | 谁定的 | 用在哪 | 特点 |
|---|---|---|---|
| **URDF** | ROS 社区 | 机械臂、ROS 生态 | 只能描述树状结构，参数少 |
| **MJCF** | MuJoCo | 仿真、控制 | 能描述接触、执行器、传感器、复杂的关节 |
| STL / OBJ | 通用 | 只存形状 | 无质量、无关节 |

转换工具存在（URDF→MJCF），但执行器增益、接触参数会丢，**转完必须手改**。

## 第 6 章 MJCF 语法详解

这一章是全书最"干"的部分。**跳过它，后面所有报错你都会看不懂。**

### 6.1 XML 的五条规则

**规则 1：一个根元素**

```xml
<mujoco model="mybot">
    <!-- 所有内容都在这里 -->
</mujoco>
```

**规则 2：标签成对**

```xml
<body name="foot">      ← 开始
    ...
</body>                  ← 结束
```

**规则 3：空元素用 `/>`**

```xml
<geom type="mesh" mesh="foot"/>
```

**规则 4：属性 = 名字 "值"，值必须加双引号**

```xml
<body name="arm1" pos="0 0 0.06">
```

**规则 5：值的三种类型**

| 类型 | 写法 | 例子 |
|---|---|---|
| 单值 | `kp="0.5"` | 数字或字符串 |
| 向量 | **用空格分隔，不能有逗号** | `pos="0 0 0.06"` |
| 布尔 | `true` / `false` | `limited="true"` |

**注释**：`<!-- 这行不会执行 -->`
**大小写敏感**：`<body>` 对，`<BODY>` 错。
**特殊字符**：`&` 写成 `&amp;`，`<` 写成 `&lt;`。

### 6.2 八段结构

一个完整的 MJCF 由这些段组成，**顺序随意**，但建议按下面写：

```xml
<mujoco model="名字">

  <!-- ① 编译设置 -->
  <compiler angle="radian" meshdir="meshes" autolimits="true"/>

  <!-- ② 物理引擎设置 -->
  <option timestep="0.001" gravity="0 0 -9.81" integrator="implicitfast"/>

  <!-- ③ 资源（网格、材质） -->
  <asset>
    <mesh name="foot" file="foot.stl"/>
  </asset>

  <!-- ④ 默认值 -->
  <default>
    <joint damping="0.02" armature="0.0001"/>
  </default>

  <!-- ⑤ 世界与刚体树（核心） -->
  <worldbody>
    <geom name="ground" type="plane" size="5 5 0.1"/>
    <light pos="1 0 1" dir="-1 0 -1"/>
    <body name="foot">
      ...
    </body>
  </worldbody>

  <!-- ⑥ 执行器 -->
  <actuator>
    <position joint="j1" kp="0.5" kv="0.04" forcerange="-0.18 0.18"/>
  </actuator>

  <!-- ⑦ 传感器（可选） -->
  <!-- ⑧ 关键帧（可选） -->

</mujoco>
```

### 6.3 逐段讲解

#### ① `<compiler>` 怎么读这个文件

| 属性 | 作用 | 常用 |
|---|---|---|
| `angle` | 角度单位 | `radian`（推荐） |
| `meshdir` | 网格目录 | `meshes` |
| `autolimits` | 有 `range` 就自动开限位 | `true` |

#### ② `<option>` 物理引擎

| 属性 | 含义 | 本工程 |
|---|---|---|
| `timestep` | 每步时长（秒） | 0.001（1 ms） |
| `gravity` | 重力向量 | `0 0 -9.81` |
| `integrator` | 积分方法 | `implicitfast`（有接触必须用） |
| `iterations` | 求解迭代次数 | 抖动时加 |

#### ③ `<asset>` 外部资源

```xml
<mesh name="内部名" file="磁盘文件名"/>
```

`name` 给后面引用，`file` 是真实文件，两者可以不同。

**单位陷阱**：STL 没有单位。SolidWorks 常导出毫米，MuJoCo 要米，两种修法：

```xml
<mesh name="foot" file="foot.stl" scale="0.001 0.001 0.001"/>   <!-- 缩放进 XML -->
```
或在 CAD 里先把单位改成米再导出。

#### ④ `<default>` 批量默认值

```xml
<default>
  <joint damping="0.02"/>
  <default class="servo">
    <position kp="0.5" kv="0.04" forcerange="-0.18 0.18"/>
  </default>
</default>
```

用的时候 `<position class="servo" joint="j1"/>`，参数自动带上。改一处全部生效。

#### ⑤ `<worldbody>` 刚体树（核心）

写法的唯一判据：

- `<body>` = 零件
- `<joint>` = 零件之间怎么连接
- `<geom>` = 零件的形状
- **缩进 = 谁装谁**

```xml
<worldbody>
  <body name="A">            ← 根零件
    <joint type="free"/>     ← 能在空间自由动
    <geom .../>

    <body name="B">          ← B 装在 A 上
      <joint type="hinge" axis="1 0 0" range="-1.57 1.57"/>
      <geom .../>
    </body>
  </body>
</worldbody>
```

#### ⑥ `<actuator>` 电机

| 类型 | 你给什么 | 内部做什么 |
|---|---|---|
| `motor` | 力矩 | 直接施加 |
| `position` | 目标角 | `力矩 = kp(目标 - 当前) - kv·速度`，再按 `forcerange` 裁剪 |
| `velocity` | 目标速度 | 保持转速 |

本工程用 `position`，因为舵机就是位置控制。

#### ⑦ `<sensor>` 传感器（可选）

不用也能训（直接读 `data` 数组）。用它的好处是名字清晰。

#### ⑧ `<keyframe>` 预设姿态（可选）

```xml
<keyframe>
  <key name="fallen" qpos="0 0 0.1 0.707 0.707 0 0 0 0"/>
</keyframe>
```

### 6.4 网格（mesh）是什么

| 表示 | 是什么 | 例子 |
|---|---|---|
| **网格** | 一堆三角形面片，只存形状 | STL、OBJ |
| 参数化实体 | 数学描述（圆柱 = 圆心+半径+高） | STEP |

CAD 里是参数化实体，但仿真器不认，要导出成网格。

STL 里只有三角形顶点，**没有单位、没有质量、没有颜色、没有关节**。

**在 MuJoCo 里的两个用途**：

```xml
<geom type="mesh" mesh="foot"/>    <!-- 好看 -->
<geom type="box" size="..."/>      <!-- 用来算碰撞（快） -->
```

标准做法：**网格负责好看，简化盒子负责碰撞**。

**凸包陷阱**：用网格碰撞时 MuJoCo 会取它的凸包（橡皮筋包起来），凹槽和内腔会被填平。所以薄壳、带凹的零件一定要单独配碰撞体。

### 6.5 自由度与 nq / nv

**自由度 = 独立运动的数量 = "你能拧几个旋钮"。**

| 物体 | 自由度 |
|---|---|
| 空中刚体 | 6（3 平移 + 3 旋转） |
| 门 | 1 |
| 本工程机器人 | 8（整机 6 + 两个舵机各 1） |

| 关节 | 允许的运动 | 剩余自由度 |
|---|---|---|
| `free` | 全放开 | 6 |
| `hinge` | 绕一个轴转 | 1 |
| `slide` | 沿一个轴滑 | 1 |
| `ball` | 绕点转 | 3 |

#### nq 与 nv 为什么不同

| 符号 | 名字 | 描述什么 | 本工程 |
|---|---|---|---|
| `nq` | 位置变量数 | "在哪" | 9 |
| `nv` | 速度变量数 | "怎么动" | 8 |

- 位置：3 个平移 + **4 个四元数** = 7
- 速度：3 个线速度 + **3 个角速度** = 6

**为什么位置用 4 个数、速度只用 3 个？** 因为姿态要防奇异（见 6.6），而速度不需要——"绕某轴转多快"天然是 3 维向量。

```
nq = 7（自由）+ 2（两个铰链）= 9
nv = 6（自由）+ 2（两个铰链）= 8
差 1 = 四元数多出来的那一位
```

验证：

```bash
python -c "import mujoco; m=mujoco.MjModel.from_xml_path('assets/robo1.xml'); print(m.nq, m.nv, m.nu)"
# 9 8 2
```

### 6.6 四元数

#### 为什么不用欧拉角

| 问题 | 后果 |
|---|---|
| 万向节死锁 | 某个角度丢失一个自由度 |
| 跳变 | 359°→1° 数值突变 358，神经网络以为世界剧变 |

#### 定义

四元数 `(w, x, y, z)` = "绕某轴转某角"。给定单位轴 `(ax, ay, az)` 和角 `θ`：

```
w = cos(θ/2)
x = ax · sin(θ/2)
y = ay · sin(θ/2)
z = az · sin(θ/2)
```

注意是**半角**。

#### 手算三个例子

| 情况 | 结果 |
|---|---|
| 不转 | `(1, 0, 0, 0)` |
| 绕 Z 转 90° | `(0.7071, 0, 0, 0.7071)` |
| 绕 X 转 90° | `(0.7071, 0.7071, 0, 0)` |

#### 三个注意点

| 点 | 说明 |
|---|---|
| 顺序是 `(w,x,y,z)` | MuJoCo 用这个。Scipy 用 `(x,y,z,w)`，抄错全乱 |
| 长度必须为 1 | `w²+x²+y²+z²=1`。MuJoCo 积分时自动归一化 |
| `q` 与 `-q` 是同一姿态 | 所以观测里用重力向量：连续、无变号问题 |

### 6.7 惯性张量

| 概念 | 衡量什么 | 公式 |
|---|---|---|
| 质量 | 推起来多难 | `F = m·a` |
| 转动惯量 | 转起来多难 | `τ = I·α` |

质量分布不对称时，绕不同轴难度不同，还要用 3×3 矩阵：

```
      ⎡ Ixx  Ixy  Ixz ⎤
  I = ⎢ Ixy  Iyy  Iyz ⎥        对称 → 只有 6 个独立分量
      ⎣ Ixz  Iyz  Izz ⎦
```

| 分量 | 含义 |
|---|---|
| `Ixx, Iyy, Izz` | 绕三轴转的惯量（恒正） |
| `Ixy, Ixz, Iyz` | 惯性积（耦合项，对称件为 0，可正可负） |

写法（**顺序必须是 ixx iyy izz ixy ixz iyz**）：

```xml
<inertial pos="质心x 质心y 质心z" mass="0.0176"
          fullinertia="7.8e-6 5.9e-6 1.1e-5 -4.4e-8 -4.4e-7 1.2e-8"/>
```

对称件可简写：

```xml
<inertial pos="0 0 0.02" mass="0.0176" diaginertia="7.8e-6 5.9e-6 1.1e-5"/>
```

**手算长方体**（长 a、宽 b、高 c，质量 m）：

```
Ixx = m(b² + c²)/12
Iyy = m(a² + c²)/12
Izz = m(a² + b²)/12
惯性积 = 0
```

例：4×3×2 cm、20 g 的盒子 → `Ixx = 0.02×(0.03²+0.02²)/12 = 2.2e-6 kg·m²`

**MuJoCo 会检查**：矩阵必须正定，主惯量要满足三角不等式（`Ixx+Iyy ≥ Izz`），否则报 `inertia matrix is not positive definite`。这通常意味着单位或坐标系弄错了。

### 6.8 name 引用机制

XML 最核心的机制：

```xml
<mesh name="foot" file="foot.stl"/>      ← 定义
<geom type="mesh" mesh="foot"/>          ← 引用

<joint name="j1" .../>
<position joint="j1" .../>
```

**同类元素的 name 必须唯一。** 代码里要用到的**必须起名**，否则只能靠数字下标，改模型必崩。

命名规则：不能有空格，建议全小写+下划线（`servo1_joint` 比 `j1` 好）。

### 6.9 常见语法错误

| 报错 | 原因 | 修 |
|---|---|---|
| `XML parse error at line N` | 标签没闭合 / 属性缺引号 | 检查那一行 |
| `unknown attribute` | 属性名拼错（`positon`） | 对照文档 |
| `expected number` | 向量里用了逗号 | `pos="0 0 0.1"` |
| `element not found` | 引用的名字不存在 | 检查 `joint="j2"` 是否定义 |
| `duplicate name` | 两个元素同名 | 改名 |
| `mesh file not found` | 路径错 | 查 `meshdir` 和文件 |
| `inertia not positive definite` | 惯量写错 | 重读 CAD |

| 量 | MuJoCo | CAD 常见 | 换算 |

### 7.3 七步手写流程（每步都验证）

#### 第 1 步 · 骨架（能加载）

```xml

    <mesh name="foot" file="foot.stl"/>
  </asset>

    </body>

```

**验证**：`nq/nv/nu = 7 6 0`

#### 第 2 步 · 惯量（有重量）

加 `<inertial/>`，**验证** `body_mass.sum()` 等于实物重量。

#### 第 3 步 · 关节（能转）

```xml
<body name="arm1" pos="0 0 0.06">
  <joint name="j1" type="hinge" axis="1 0 0" pos="0.0607 -0.079 0.0996"
         range="-1.5708 1.5708" damping="0.02" armature="0.0001"/>
  ...
</body>
```

| 参数 | 含义 | 怎么定 |
|---|---|---|
| `axis` | 转轴 | 看舵机装法 |
| `pos` | 轴的位置 | 从 CAD 量 |
| `range` | 限位 | 舵机 180° → ±1.5708 |
| `armature` | 转子惯量折算 | 1e-4 量级，能稳定训练 |

**验证方向（最容易反）**：

```bash
d.qpos[7]=0.8; mujoco.mj_forward(m,d); print(d.body('arm1').xpos)"
```

方向反了就把 `axis` 取负。

#### 第 4 步 · 执行器（有力气）

```xml
<actuator>
  <position name="a1" joint="j1" kp="0.5" kv="0.04"

</actuator>
```

**`forcerange` 查舵机规格**：

| 舵机 | 堵转力矩 | N·m |
|---|---|---|
| MG90S @4.8V | 1.8 kg·cm | 0.176 |
| MG90S @6V | 2.2 kg·cm | 0.216 |
| SG90 | 1.2 kg·cm | 0.118 |

> 本工程模型写的是 ±1.0 N·m（原作者设定），比真实舵机大 5 倍——这是"训练容易、上机偏乐观"的取舍。

#### 第 5 步 · 碰撞（能站住）

```bash
mujoco.mj_forward(m,d); print(d.ncon, [round(c.dist,4) for c in d.contact[:d.ncon]])"
```

预期 `ncon>0`、`dist≈-0.0001`。

### 7.5 参数从哪来

| 参数 | 来源 | 难度 |
|---|---|---|
| `mass` | 电子秤 或 CAD | 易 |
| `pos`（质心） | CAD | 易 |
| `fullinertia` | CAD 或几何公式 | 中 |
| `range` | 舵机行程 | 易 |
| `forcerange` | 舵机规格书 | 易 |
| `kp / kv` | 试（0.5 / 0.04 起步） | 经验 |
| `damping` | 试（0.01～0.05） | 经验 |
| `armature` | 试（1e-4） | 经验 |
| `timestep` | 0.001 起步 | 易 |

**前五个必须准，后四个可以调。**

### 7.6 碰撞分组：contype / conaffinity

MuJoCo 用**位掩码**判断两个 geom 是否碰撞：

```
(contype_A & conaffinity_B) != 0  或  (contype_B & conaffinity_A) != 0
```

默认都是 1，所以 1&1=1 → 碰。

| 意图 | 写法 |
|---|---|
| 正常碰撞 | 不写（默认 1/1） |
| 只显示不碰 | `contype="0" conaffinity="0"` |
| 分组控制 | `contype="2" conaffinity="1"` 配合地面 `contype="1"` |

> 本工程的坑：所有 `*_collision` 盒子都被设成 `contype=0`（不碰），实际靠可见 mesh 的凸包在碰。能跑，但和常规做法相反。

## 第 10 章 阶段 2 · 写 MDP

### 10.1 一页纸模板

**先填表，再写代码。**

| 问题 | 本工程的答案 |
|---|---|
| 目标 | 从四种跌倒姿态起立并保持 |
| 成功 | 倾角≤14.32° + 关节≤0.12 + 基座速度≤0.25 + 持续 1 秒 |
| 失败 | 连续 0.5 秒无接触、数值发散 |
| 动作 | 2 个数 ∈[-1,1]，关节目标角增量 |
| 观测 | 10 个数（重力 3 + 关节 2 + 角速度 2 + 上帧目标 2 + 高度 1） |
| 奖励 | 直立 1.0 + 关节归位 0.75 + 进展 0.2 − 抖动 − 甩动；成功 +10，失败 −5 |
| 回合长度 | 14 秒（50 Hz → 700 步） |
| 初始状态 | 四姿态之一，±15° 扰动，关节 ±0.15 |

### 10.2 六个决定，按顺序做

```
目标 → 成功判据 → 动作 → 观测 → 奖励 → 终止
```

顺序错就要返工，因为后面的决定依赖前面。

### 10.3 观测五原则

**① 马尔可夫性（最重要）**

观测必须包含"做决策所需的全部信息"。检查方法：**把它给一个不知道历史的人，他能判断下一步该做什么吗？**

| 观测 | 够吗 | 为什么 |
|---|---|---|
| 只有倾角 | ❌ | 不知道手臂在哪，也不知道是否在动 |
| +关节角 | ❌ | 不知道速度 |
| +角速度 | ✅ | 能判断姿态与趋势 |
| +上帧目标 | ✅✅ | 舵机是位置控制，需要知道自己下过什么命令 |

**② 连续、无跳变**：用重力向量而不是 roll/pitch（后者在 90° 附近跳变、死锁）。

**③ 不塞无关信息**：删掉这一维，任务还能成吗？能就删。

**④ 量纲合理**：差异巨大时归一化。

**⑤ 有边界**：`spaces.Box(low, high)`，方便 clip。

### 10.4 奖励五原则

**① 每一顶都要能回答"策略会怎么作弊"**

| 项 | 作弊方式 |
|---|---|
| 直立分 | 站着不动（哪怕歪着） |
| 进展分 | 无法作弊（必须真的变直） |
| 关节归位分 | 折起手臂躺好 → 所以要用直立度门控 |
| 高度罚 | **本工程的坑**：用错了量，导致站起来倒扣分 |

**② 形状比权重更重要**

本工程真实教训：关节归位项用高斯函数，在 1.57 rad 处等于 `exp(-38.9)≈0`，**梯度是 0，权重再大也传不回去**。改成线性斜坡后立刻见效。

**③ 每步奖励在 1 的量级**，终局奖励在 10 的量级。

**④ 必须有稠密项**。只有"成功 +10"的话，700 步里一个信号，随机探索几乎碰不到。

**⑤ shaping 不能改变最优策略**。安全做法是"基于势"：只奖励"离目标更近了"，不奖励"现在离目标多近"。

本工程 `progress` 项就是这样：`0.2 × max(0, 上一步直立度 − 当前)`。

### 10.5 终止与截断

```python
terminated = success or failed        # 自然结束
truncated  = (time >= max_time) and not terminated   # 超时
```

| 返回 | 含义 | 后续价值 |
|---|---|---|
| `terminated` | 真的结束了 | V=0 |
| `truncated` | 被我们截断 | 还要估 |

混用会让价值函数学偏，表现为"回报上不去"。

### 10.6 动作空间三种方案

| 方案 | 数学形式 | 优点 | 缺点 |
|---|---|---|---|
| **力矩** | `τ = a × τ_max` | 最接近物理，能做任意动作 | 难训（要自己学稳定控制）、需要 200 Hz+、**普通舵机做不到** |
| **绝对角度** | `q* = a × 1.55` | 直观，与舵机原生接口一致 | 一步可跳 89°，撞限位；探索噪声被放大 20 倍 |
| **增量角度**（本工程） | `target = clip(target + 0.08·a, ±1.55)` | 有界、平滑、易迁移、噪声小 | 转到位需要多步；引入积分环节 |

**噪声放大对比**（探索噪声 σ=0.5）：

| 方案 | 每步实际角度变化 |
|---|---|
| 绝对角度 | ±0.78 rad（±45°） |
| 增量角度 | ±0.04 rad（±2.3°） |

这就是"增量更好训"的量化原因。

**0.08 与 1.55 的由来**：

- `0.08 rad / 0.02 s = 4 rad/s ≈ 229°/s`，约为 MG90S 最大速度（600°/s）的 1/3
- 舵机行程 180° = ±1.5708，留 0.02 余量 → 1.55

**这三个数必须和固件一致。**

### 10.7 Gymnasium 代码骨架

```python
import gymnasium as gym
import numpy as np
from gymnasium import spaces


class MyEnv(gym.Env):
    def __init__(self):
        self.action_space = spaces.Box(-1.0, 1.0, shape=(2,), dtype=np.float32)
        self.observation_space = spaces.Box(
            low=np.array([-1,-1,-1,-1.6,-1.6,-20,-20,-1.6,-1.6,-0.1], np.float32),
            high=np.array([1, 1, 1, 1.6, 1.6, 20, 20, 1.6, 1.6, 0.5], np.float32),
            dtype=np.float32,
        )
        self.time = 0.0
        self.target = np.zeros(2)
        self.max_time = 14.0

    def reset(self, *, seed=None, options=None):
        super().reset(seed=seed)          # 必须，否则 np_random 不存在
        self.time = 0.0
        self.target = np.zeros(2)
        # ... 设初始姿态、让物理稳定
        return self._obs(), {"pose": "roll_pos"}

    def step(self, action):
        action = np.asarray(action, dtype=np.float64)
        self.target = np.clip(self.target + 0.08 * action, -1.55, 1.55)
        self.data.ctrl[0], self.data.ctrl[1] = self.target
        for _ in range(20):                # 20 × 1ms = 20ms
            mujoco.mj_step(self.model, self.data)
        self.time += 0.02

        # 成功判定
        ok = self._tilt_deg() <= 14.32 and np.max(np.abs(self._joints())) <= 0.12 \
             and np.linalg.norm(self.data.qvel[:3]) <= 0.25
        self.hold = self.hold + 0.02 if ok else 0.0
        success = self.hold >= 1.0
        failed = self._diverged()

        reward = self._reward(action, success, failed)
        terminated = success or failed
        truncated = (self.time >= self.max_time) and not terminated
        return self._obs(), float(reward), terminated, truncated, {"is_success": success}

    def _obs(self):
        return np.concatenate([...])       # 必须和 observation_space 维度一致
```

**三个 API 约定**：

| 约定 | 说明 |
|---|---|
| `reset()` 返回 `(obs, info)` | Gymnasium 0.26+ |
| `step()` 返回 **5 个**值 | `(obs, reward, terminated, truncated, info)` |
| 必须 `super().reset(seed=seed)` | 否则随机性不可复现 |

### 10.8 折扣因子 γ

`有效视野 ≈ 1/(1-γ)` 步。

| γ | 视野 | 适合 |
|---|---|---|
| 0.9 | 10 步 | 太短 |
| **0.99** | 100 步（2 秒） | 起立这种 2～3 秒的动作 |
| 0.999 | 1000 步 | 太长，方差大 |

## 第 12 章 阶段 4 · 做基线

### 12.1 什么是基线

**不用学习就能做到的参照物。** 没有基线，你永远不知道 78% 是好是坏。

### 12.2 关键帧

**关键帧 = "某时刻各关节应在什么角度"的表格**，中间用线性插值补。

本工程 `roll_pos` 的 7 帧：

| 时刻(s) | 关节 1 | 关节 2 | 动作含义 |
|---|---|---|---|
| 0.02 | 0.087 | 0.085 | 起始 |
| 0.34 | 1.481 | 1.441 | 甩出去 |
| 0.36 | 1.526 | 1.403 | 最大 |
| 0.68 | 1.549 | 0.110 | 第二关节回收 |
| 0.70 | 1.461 | 0.066 | 继续 |
| 1.02 | 0.044 | 0.002 | 第一关节回收 |
| 1.04 | 0 | 0 | 归零 |

物理意义：甩臂积累角动量，回收时传给身体，把身体"撬"起来。

### 12.3 关键帧 → 增量动作

```python
desired = target_at(时间)                # 查表 + 插值
delta   = (desired - 当前target) / 0.08  # 折算成还差几个增量
action  = clip(delta, -1, 1)
```

数值例子（第一步）：`[0.087,0.085] - [0,0]` → `/0.08` → `[1.09,1.06]` → clip → `[1,1]` → `target = 0.08`。

### 12.4 开环 vs 闭环

| | 开环 | 闭环 |
|---|---|---|
| 输入 | 只有时间 | 实际状态 |
| 类比 | 微波炉定时 | 空调测温 |
| 扰动下 | 会垮 | 能修正 |

基线是**开环**的：它不看倾角、重力、关节实际角度，只按时间表播放。

### 12.5 为什么基线 100% 不代表任务完成

| 条件 | 成功率 |
|---|---|
| 标称（起始角精确） | **100%** |
| 带 ±15° 扰动 | 明显下降 |

**100% 说明"这条示范路线可行"，不说明"任务被解决了"。**

### 12.6 基线的三个用途

1. **验证环境**：基线都做不到 100%，说明环境/参考数据有问题
2. **提供对照**：RL 和基线在同一张表上比
3. **提供示范**：`(观测, 动作)` 对可直接用于行为克隆（作者的流程就是 `engine="bc"`）

**关卡 4**：基线 ≥ 90%。

## 第 14 章 阶段 6 · 诊断（最重要的一章）

### 14.1 判断框架

| 症状 | 第一嫌疑 | 验证手段 |
|---|---|---|
| 程序报错 | 代码 | traceback |
| 不报错但物理怪（穿地、飞走、卡住） | 模型/物理参数 | 打印 `qpos`、`ncon`、`contact.dist` |
| 能跑但学不会 | 奖励/终止 | 打印每一项奖励 |
| 学得会但结果不对 | 成功判定 | 手算一条轨迹 |

### 14.2 案例一：reset() 就崩

```
IndexError: too many indices for array: array is 1-dimensional, but 2 were indexed
```

定位：`selftest` 吞了 traceback，直接跑 `SelfRisingEnv()` 拿到行号：

```python
self.data.ctrl[self.idx.actuator_ids] = 0.0    # actuator_ids 是元组 (0,1)
```

**NumPy 把元组下标当多维下标**：`arr[(0,1)]` == `arr[0,1]`。改成 `list(...)`。

**教训：下标是元组还是列表，在 NumPy 里语义完全不同。**

### 14.3 案例二：回合 0.2 秒就结束

现象：四姿态全部 0.2～0.7 秒结束，末态倾角还有 11°。

查法：打印 `h=qpos[2]`、`ncon`、`|qvel|`：

```
t=0.02 h=0.125   t=0.32 h=0.070   t=0.64 h=-0.051  ← 触发 h < -0.05
```

但空放 200 步（不控舵机）时 `h` 稳定在 0.125、`ncon=4`，根本不掉。

**结论：`qpos[2]` 不是高度**，它是根 body 坐标系原点的 z，而原点在几何体外面，站直过程中会掉到 0 以下。

修复：失败判定改成"连续 0.5 秒无接触点"。

**教训：用一个量之前先确认它的物理含义。名字叫 height 不代表它是高度。**

### 14.4 案例三：能站起来，但成功率永远 0

**第一轮**：`ep_len` 死贴 701，回报 -508 → -28 后倒退到 -173。

打印奖励明细，发现高度项：

```
-50 × (h - 0.08)²，站立时 h=-0.05 → 每步 -0.85
```

而站直奖励只有 +1.0。**站起来倒扣分，躺着才不扣。**

修复一：删掉高度项 → 回报变成 +684 平台。

**第二轮**：684/701 ≈ 0.97/步，而"站直+关节归位"应是 1.75/步。打印轨迹：

```
t=2.02  tilt=0.2  q=[1.57 -1.55]  |v|=0.00
```

站得完美，但关节顶死在机械限位。

修复二：关节奖励原本是高斯 `exp(-Σq²/2σ²)`，在 1.57 处 `≈ exp(-38.9)` —— **梯度为 0**。改成线性斜坡：

```python
closeness = 1 - Σq² / (2·limit²)
```

改完：成功率 0 → 55%（训练），评测 100%。

**教训：奖励的形状比权重更重要。**

### 14.5 案例四：策略"学会了拒绝成功"

这是本工程最隐蔽的一个 bug，也是**唯一一个"策略完全理性却行为错误"**的案例。

#### 现象

在鲁棒环境（±25° 扰动 + 1 步延迟 + 观测噪声 + 域随机化）里从零训练 150 万步：

```
success_rate   : 全程 0
ep_len_mean    : 701（从未提前结束）
ep_rew_mean    : 714  ≈ 1.02/步
```

然后用已经会站立的模型热启动微调 50 万步：

```
success_rate   : 冲到 100% → 掉回 0%
ep_rew_mean    : 涨到 1154（比之前的 753 更高）
ep_len_mean    : 从 135 涨回 701
```

**成功率上去了又掉下来，回合长度从 135 涨回 701** —— 看起来像"训练不稳定"，很容易误判成超参问题。

#### 真正的诊断

把两种行为的收益算出来就明白了：

| 行为 | 一回合能拿多少分 |
|---|---|
| **赖着不动**（站在 15°，撑满 701 步） | 701 × 1.65 = **1154** |
| **2.7 秒成功站起**（135 步就结束了） | 135 × 1.75 + 10 = **246** |

**差 908 分。**

根因是两个设计的相互作用：

```
每步给奖励  +  成功就提前结束回合  =  成功反而亏钱
```

提前成功等于**主动放弃**后面 566 步的分数，而 `成功 +10` 这个终端奖励根本补不回来。所以策略拒绝成功是**完全理性**的——它在最大化你给它的奖励。

#### 修复

让成功时把"剩余步数的满分"一次性补给策略：

```python
if success:
    ceiling = cfg.w_upright + cfg.w_joint_goal          # 每步满分 = 1.75
    terms["success"] = cfg.w_success + cfg.w_success_horizon * remaining_steps * ceiling
```

于是：`135×1.75 + 10 + 566×1.75 = 701×1.75 + 10 = 1237` —— **成功 = 这一回合的理论满分**，永远不会比赖着差。

| 行为 | 修复前 | 修复后 |
|---|---|---|
| 完美赖着 | 1154 | 1157 |
| 成功站起 | **246** | **1237** |
| 结论 | 拒绝成功 ✅理性 | 追求成功 ✅理性 |

#### 结果（同起点、同环境、只改这一个逻辑）

| 训练方式 | 步数 | 评测成功率 |
|---|---|---|
| 从零训（鲁棒环境） | 150 万 | **0%** |
| 热启动（奖励仍有这个 bug） | 50 万 | **0%**（回报却高达 1154） |
| **热启动 + 修复本 bug** | **50 万** | **100%** |

#### 教训

**指标"看起来像不稳定的抖动"，可能是一个精确的激励错误。**

判断方法：**当策略的行为和你期望的相反时，先算一遍"它现在这么做能拿多少分"**。如果它选的那条路分更高，那就不是策略的问题，是奖励的问题。

这个 bug 有三个特征，值得记住：

1. 策略不报错、不崩、数值正常
2. 行为完全理性（它在最优化你给的奖励）
3. 修复只需要改一行逻辑，不是调参

### 14.6 通用动作顺序

1. **先看指标，不看代码**：哪个指标不对？什么时候开始不对？
2. **打印物理量**，不要猜
3. **对照一条完整轨迹**，找"从哪一步开始偏离预期"
4. **分三类**：代码错 / 物理参数错 / 奖励设计错
5. 修复后**只改一个变量**，重跑

|---|---|---|---|

| 现象 | 结论 |
|---|---|

| ④ 掉 | 某些物理参数组合下能力不足 → 这是 sim2real 的真实缺口 |
| 全不掉 | 策略很稳，可以直接上板 |
| 时间变长 | 策略在"求稳"，属于正常代价 |

④ 掉到 80% 的那个姿态，用时会从 2.3 秒涨到 4.6 秒——说明那 2 次是**跑满 14 秒都没起来**，不是"起来了又倒"。

```
  权重 : max|w| = 1.1000
```

`max|w| = 1.1` 不是被裁剪过——导出脚本只打印不裁剪，这是模型真实的权重量级（对 float32 完全安全）。

#### 第 2 步 · 校验「C 代码和 Python 算的一不一样」

**这一步能省掉几小时的硬件调试。**

```bash
.venv/bin/python tools/check_policy_export.py \
  runs/ppo_robust_ft2/final_model.zip firmware/include/policy.h
```

```
结构     : 10 -> 64 -> 64 -> 2   激活: elu
权重 4864 个 / 偏置 130 个（应为 4864 / 130）
[A] 头文件→numpy vs [B] torch : 最大误差 8.658e-07
[OK] 头文件的前向计算与训练模型一致，可以编译烧录。
```

工具做三段对照：头文件解析出的前向、训练模型的 torch 子模块、`model.predict()`。

| 对照 | 判什么 |
|---|---|
| A vs B | **导出是否正确**（展平顺序、层顺序、维度） |
| B vs C | `predict` 的动作裁剪差异，无害 |

如果 A vs B 不一致，最常见的原因是**行/列优先搞反**：`policy_runtime.h` 按 `W[i*in_dim + j]` 读，导出若按列展平，编译器、烧录、串口都不会报错，只是板子上的动作是错的。

#### 一个真实的坑：中文注释变乱码

从 VM 传出来的 `policy.h` 在 Windows 编辑器里打开是：

```
//  policy.h 鈥斺€� 鐢� tools/export_policy.py 鑷姩鐢熸垚
```

这是 **UTF-8 被按 GBK 解码**的结果。**不影响编译**（都是 `//` 注释），但没法读。

修法是生成时就带 BOM：

```python
out.write_text(text, encoding="utf-8-sig")   # utf-8-sig = 带 BOM
```

已经生成的文件，在编辑器里「重新以 UTF-8 打开 → 另存为 UTF-8 with BOM」也能救。

**教训：跨平台生成的文件，编码要显式指定，别依赖环境默认值。**

推 GitHub 用的 SSH 密钥包：

|---|---|

## 第 27 章 20 个常见误区

1. 以为 MJCF 是 CAD 自动生成的——它是手写的
2. 忘了给 CAD 零件赋材质（质量为 0）
3. STL 单位是毫米，直接放进 MuJoCo
4. 用欧拉角做观测（跳变、死锁）
5. 观测缺"上一帧动作"（位置控制的记忆）
6. 只有稀疏奖励就想学会
7. 奖励项量纲失衡（某项 1000/步）
8. 用没有物理意义的量做判定（本工程的 `qpos[2]`）
9. `terminated` 和 `truncated` 混用
10. 训练前不写自检
11. 没有基线就开始训练
12. 用 rollout 指标判断真实能力
13. 忽略"回合变短导致回报下降"
14. 奖励形状是高斯却怪权重不够
15. 在 Windows 上用 `forkserver`（Linux 专属）
16. 把 `.deploy/` 打包分享出去
17. 改了 `env.*` 却复用旧曲线
18. 忘了 `super().reset(seed=seed)`
19. 直接上 200 万步（应该先跑 30 万步验证）
20. 认为仿真 100% 就等于真机没问题

这一节把本工程**真实发生过的**调试过程按时间顺序记下来。它比任何"标准流程"都有用，因为真实工程就是这样：**大部分时间不是在写代码，而是在判断哪里错了。**

### F.1 时间线总览

| 次序 | 做了什么 | 结果 | 学到什么 |
|---|---|---|---|
| ① | 从零训练，原始奖励（含假高度罚） | 回报 -508 → 峰值 -28 → **倒退到 -173**，成功率 0 | 奖励里有个量是错的 |
| ② | 删掉假高度罚 | 回报 684 平台，成功率仍 0 | 还有第二个问题 |
| ③ | 关节奖励改线性斜坡 | 成功率 **55%**，评测 **100%** | 奖励的形状比权重重要 |
| ④ | 鲁棒环境从零训 150 万步 | 成功率 **0%** | 任务太难，从零学不动 |
| ⑤ | 热启动微调 50 万步 | 成功率 0%，但回报涨到 1154 | 它在拿分，只是不"成功" |
| ⑥ | 修「成功反而不划算」 | 成功率 **100%**，压力测试 **98%** | 激励错误会让策略拒绝正确行为 |

**六步里，只有 ⑤ 是"调参"，其余全是修 bug。**

### F.2 每一步的细节

#### ① 第一次训练：回报先涨后跌

```
ep_rew_mean : -508 → 峰值 -28（10 万步）→ -173（30 万步）
ep_len_mean : 701（从未变过）
success_rate: 0
```

`ep_len` 恒定说明回合从未终止——**既没成功，也没失败**。回报倒退说明策略在"学歪"。

诊断：把每一项奖励打印出来，发现高度项

```
-0.5 × 100 × (h - 0.08)²     站立时 h = -0.05  →  每步 -0.85
```

而站直的奖励只有 +1.0。**站起来要倒扣分，躺着才不扣。**

根因：`h` 取的是 `qpos[2]`，即根 body 坐标系原点的 z 值，而原点在几何体之外。

#### ② 删掉高度罚：回报涨到 684，成功率还是 0

```
ep_rew_mean : 205 → 684（12.8 万步后完全平台）
ep_len_mean : 701
success_rate: 0
```

684 ÷ 701 ≈ 0.97/步，而「站直 + 关节归位」应该是 1.75/步 → **关节那部分一分没拿**。

打印轨迹：

```
t=2.02  tilt=0.2  q=[1.57 -1.55]  |v|=0.00  r=+1.00
```

站得完美，但两个关节顶死在机械限位 ±1.57 上。

#### ③ 关节奖励改线性：成功率 0 → 55%，评测 100%

原来的关节奖励是高斯 `exp(-Σq²/2σ²)`，在 1.57 rad 处 `≈ exp(-38.9) ≈ 0`——**梯度为零**，策略根本不知道"转回 0 有奖励"。

改成线性斜坡后：

```
success_rate: 0 → 8% → 31% → 55%
ep_len_mean : 701 → 679 → 594 → 481
```

评测（确定性动作）直接 **100%**，平均 2.6～2.8 秒。

#### ④ 鲁棒环境从零训练：0%

把环境加到最难（±25° 扰动 + 1 步延迟 + 观测噪声 + 域随机化），从零训 150 万步、57 分钟：

```
ep_rew_mean : 714   ≈ 1.02/步
ep_len_mean : 701   （一次都没提前结束）
success_rate: 0
```

又落回"站住但关节顶死"的局部最优，150 万步没跳出来。

#### ⑤ 热启动微调：回报涨了，但成功率还是 0

用已经会站立的模型当起点，只学"适应扰动"，50 万步：

```
success_rate: 冲到 100% → 掉回 0%
ep_rew_mean : 753 → 1154
ep_len_mean : 135 → 701   ← 回合又变长了
```

表现很像"训练不稳定"，但其实是**精确的激励错误**：

| 行为 | 一回合收益 |
|---|---|
| 赖着不动（站在 15°，撑满 701 步） | 701 × 1.65 = **1154** |
| 2.7 秒成功站起（135 步就结束） | 135 × 1.75 + 10 = **246** |

**早点成功 = 主动放弃后面 566 步的分数。** 策略拒绝成功是完全理性的。

#### ⑥ 修复后：100%

成功时把"剩余步数 × 每步满分"补给策略：

```python
if success:
    ceiling = cfg.w_upright + cfg.w_joint_goal          # 1.75
    terms["success"] = cfg.w_success + cfg.w_success_horizon * remaining_steps * ceiling
```

`135×1.75 + 10 + 566×1.75 = 1237` = 这一回合的理论满分。

结果（同起点、同环境、只改这一个逻辑）：

| 训练方式 | 步数 | 评测成功率 |
|---|---|---|
| 从零训（鲁棒环境） | 150 万 | 0% |
| 热启动（奖励仍有 bug） | 50 万 | 0%（回报却高达 1154） |
| **热启动 + 修复本 bug** | **50 万** | **100%** |

### F.3 四次训练的成本

| 配置 | 步数 | 速度 | 耗时 | 结果 |
|---|---|---|---|---|
| 从零（v1→v3） | 30 万 × 3 | 420 步/秒 | 约 36 分钟 | 100%（±15°） |
| 从零（鲁棒） | 150 万 | 435 步/秒 | 约 58 分钟 | 0% |
| 热启动（有 bug） | 50 万 | 432 步/秒 | 约 19 分钟 | 0% |
| 热启动（修复后） | 50 万 | 432 步/秒 | 约 19 分钟 | **100%（±25°+全扰动）** |

### F.4 这六步提炼出的通用规律

| 现象 | 别急着调超参，先查 |
|---|---|
| 回报见顶后倒退 | 奖励里有没有"能被套利"的项 |
| `ep_len` 恒定不变 | 成功/失败条件是不是永远不可达 |
| 回报很高但成功率 0 | 策略是不是在"拿分但没完成任务" |
| 成功率冲高又回落 | 成功是否比"不成功"更亏 |
| 从零在难环境学不动 | 换成热启动（课程学习） |
| 局部最优卡住不动 | 奖励的形状（梯度）而不是权重 |

**最后一条最重要**：本工程三次"学不会"，两次是奖励形状的问题（梯度为 0 / 成功反而亏），一次是量用错了（`qpos[2]` 不是高度）。**没有一次是超参问题。**
