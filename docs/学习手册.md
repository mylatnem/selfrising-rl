## 前言：这本手册怎么用

这本手册配一个工程：selfrising-rl。工程里是一台 2 自由度的小机器人（一个底座、两个舵机、会倒也会自己爬起来），用 MuJoCo 做仿真，用 PPO 学一个起身策略。模型和参考动作都是真的，训练与评估代码是为教学重写的。

它和网上大多数教程的区别在三个地方，也决定了你应该怎么用它：

- 每一步都有验收标准。不是“跑完就行”，而是“跑到什么现象算对”。
- 每个概念都能在代码里找到落点。讲“观测”就一定告诉你在哪个文件哪一行。
- 所有数字都来自这个工程，不是编的。步长 1 ms、控制 50 Hz、成功判据 14.32°，都能在文件里找到。

建议的用法是三种：

- 第一次读：从第 0 章开始顺着做，一章不要跳，尤其是第 3、4 章。
- 第二次读：直接跳到你要改的那一节，当参考手册用。
- 卡住时：先看第 8 章排错表，再看第 9 章自测题，最后才去搜。

正文里的约定：灰底等宽字是命令或代码，都要在工程根目录（能看到 requirements.txt 的那一层）执行；带“你应该看到”的段子是验收点，对不上就不要往下走。

开始前请准备三样东西：一台能装 Linux 虚拟机的电脑；一个记事本（真的记事本，用来记录每次实验的参数和结果）；以及一点耐心——这个工程第一次跑通需要两三个小时，但后面每一次实验都会快很多。

## 序章：一张地图，看清机器学习与仿真

这一章不训练、不写代码，只做一件事：给你一张地图。学完之后，你听到一个新名词时能立刻把它归到某一层，知道它是干什么的、能换成什么、什么时候不需要。这比背定义有用得多。

为什么先看地图？因为初学者最大的困扰不是“这个算法好难”，而是“这些词到底是什么关系”——MuJoCo 和 PyTorch 是什么关系？ONNX 和 ROS 2 挨着吗？为什么又要装 gymnasium，又要装 stable-baselines3？一张图就能把这些结拆开。

### 一、先把三件事分开

整个领域看着很庞大，其实只包含三件事。把它们混成一团，是很多困惑的根源：

**表 1  三件事**

| 这件事 | 回答的问题 | 由什么负责 |
| --- | --- | --- |
| 仿真 | 世界怎么算（重力、碰撞、摩擦） | 物理引擎，例如 MuJoCo |
| 学习 | 策略怎么来（从试错里找规律） | 优化算法，例如 PPO |
| 部署 | 策略怎么用（在真机上跑起来） | 嵌入式与系统工程 |

本手册的内容就是这三件事按顺序排下来：第 2～4 章是仿真，第 5～6 章是学习，第 7 章是部署。

### 二、六层框架：从想法到机器人动起来

把上面三件事再拆细一点，就是六层。每一层都可以换工具，只要接口不变，上面的层就不用改——这就是为什么你能把 MuJoCo 换成 Isaac Lab，策略代码却几乎不动。

这张表还有一个用途：当你听到别人说“我们用 Isaac Lab 训的”，你就知道那是第 2、3 层的事，与你第 1 层的 MDP 设计无关；听到“部署在 ROS 2 上”，那是第 5 层，也不影响你怎么写奖励。

**表 2  六层框架**

| 层 | 它解决什么 | 本项目用的 | 常见替代 / 什么时候换 |
| --- | --- | --- | --- |
| 1 问题定义 | 观测、动作、奖励怎么写 | 你手写（第 2 章） | 没有工具，只有设计 |

### 三、仿真层：那些模型格式与物理名词

这一层只干一件事：给定初始状态和控制量，算出下一步的状态。名词看起来多，其实只分三类——模型格式、物理概念、数值参数。

把 MJCF、URDF、USD 理解成三种“方言”：说的是同一件事（机器人长什么样），但语法和侧重不同。MJCF 偏动力学，URDF 偏装配，USD 偏场景与渲染。

**表 3  仿真层名词**

| 名词 | 一句话 | 在本工程里 |
| --- | --- | --- |
| MJCF | MuJoCo 的模型格式（XML） | assets/robo1.xml |
| URDF | ROS 系的模型格式，偏运动学与装配 | 本工程不用 |
| USD | Isaac Sim / Omniverse 的场景格式 | 本工程不用 |
| 刚体 / 关节 | 有质量的物体 / 两物体间的约束 | foot、arm1、arm2 / 两个 hinge |
| 执行器 | 驱动关节的东西 | 两个 position 舵机 |
| timestep / decimation | 物理步长 / 每控制步走几次 | 1 ms / 20 次 |

### 四、学习层：算法名词到底在说什么

这一层的名词最多，但它们都在回答同一个问题：怎么根据分数调整策略。记住这句话，下面的词就都好归位了。

**表 4  学习层名词**

| 名词 | 一句话 | 在本工程里 |
| --- | --- | --- |
| MDP | 把问题写成观测/动作/奖励/终止四件事 | 第 2 章整章 |
| 策略 | 观测到动作的函数 | 10 进 2 出的小网络 |
| 价值函数 / 优势 | 估计能拿多少分 / 比估计好多少 | PPO 内部的 critic |
| on-policy / off-policy | 只用新数据 / 可复用旧数据 | PPO 属于前者 |
| 熵 / clip | 随机程度 / 每次允许改多少 | 控制探索与稳定性 |
| 域随机化 | 训练时随机改参数，提升鲁棒性 | ppo_robust |

一个反直觉的提醒：算法名字不等于能力。PPO 不是“比 SAC 更好的算法”，而是“更稳、更省心、更适合新手”的算法。你在这个工程里学到的调参直觉，换到 SAC 上一样能用。

### 七、五层之间是怎么流动的

把一次完整的训练想象成一条流水线：你在第 1 层写下 MDP（观测、动作、奖励、终止）；第 2 层用 MJCF 把这个机器人描述出来，物理引擎按 1 ms 一步往下算；第 3 层反复采样与更新，把“哪个动作更容易得分”的经验压进一个神经网络的参数里；第 4 层把这些参数导成一个文件；第 5 层把它烧进芯片，每 20 ms 读一次传感器、算一次动作、发给舵机。

这五个环节里，任何一环错了，整条链都跑不起来，但错的表现完全不同：第 1 层错了是“学不会”，第 2 层错了是“动作奇怪”，第 3 层错了是“不收敛”，第 4 层错了是“装不上”，第 5 层错了是“仿真里能站、实物上倒”。学会按现象定位到层，就是这本手册想教你的核心能力。

最后一句提醒：名词不是知识。背下“PPO 是近端策略优化”没用，能说出“它在限制每次更新的幅度，所以训练曲线更平滑”，才是真的懂了。接下来每一章，都会把名词还原成这句话。

## 第 0 章 预备知识：先把直觉建立起来

这一章不写一行代码。它只做一件事：让你在动手之前，脑子里先有三个正确的图景。很多人学不下去，不是因为数学不够，而是因为一开始就把“仿真”“强化学习”“策略”这几个词理解歪了。

### 0.1 三个必须先建立的直觉

#### 直觉一：仿真是一个可以无限重来的世界

真机上，机器人摔倒一次就要人扶起来，舵机还可能扫齿；一天能做几十次尝试就不错了。而在 MuJoCo 里，一个回合只要十几秒，一天可以跑几十万次，而且每次都从完全相同的姿势开始。

这就是“仿真”的全部意义：它把“试错”的成本从“几分钟 + 硬件损耗”降到“几毫秒 + 零成本”。强化学习需要的正是海量试错，所以它几乎总是从仿真开始。

但要记住它的代价：仿真里的世界只是真实世界的一个近似。近似得不好，学出来的策略就“只会考试、不会干活”。本手册第 7 章讲的 sim2real，就是在处理这个差距。

#### 直觉二：强化学习就是“试错 + 打分 + 记住”

想象教一个小孩骑车。你不会给他推导力学方程，你只会：让他试（试错），摔倒了下一次调整（反馈），成功了夸一句（奖励），练多了形成肌肉记忆（策略）。

强化学习把这件事变成了算法：机器人在仿真里反复尝试，每一步根据“做得好不好”得到一个分数（奖励），算法根据分数调整自己的行为方式，直到分数稳定变高。

这里有个关键区别：它学的不是“标准答案”，而是“在什么情况下做什么动作更容易得高分”。所以奖励设计得好不好，直接决定了它学会的是不是你想要的。

#### 直觉三：策略是一个“看到什么就做什么”的函数

训练结束后你得到的东西，本质上就是一个函数：输入当前看到的信息（观测），输出要执行的动作。它的内部可能是一个只有几层的小神经网络，也可能只是一张表。

理解这一点很重要，因为它意味着：部署到真机时，你只需要把真机的传感器读数喂给这个函数，把它输出的动作发给舵机。不需要把整个训练环境搬过去。这也是为什么后面能用几十 KB 的 ONNX 文件把策略烧进单片机。

### 0.2 五个词，一次说清

下面五个词会贯穿全书。先混个脸熟，读到后面再回来对一遍。

**表 7  五个核心术语**

| 词 | 一句话解释 | 在这台机器人上具体是什么 |
| --- | --- | --- |
| 观测（observation） | 策略每一步能“看到”的信息 | 重力方向、两个关节角、角速度、上次的目标角、身体高度 |
| 动作（action） | 策略每一步能“做”的事 | 两个舵机目标角各自再转多少，范围 [-1, 1] |
| 奖励（reward） | 每一步得到的分数 | 站得越直分越高，动作抖、高度不对、失败都会扣分 |
| 策略（policy） | 从观测到动作的函数 | 一个 10 进 2 出的小神经网络 |
| 回合（episode） | 一次完整的尝试 | 从跌倒姿态开始，到站起来保持 1 秒，或超过 14 秒为止 |

### 0.3 为什么不直接写控制程序

这是初学者最常问的问题：不就两个关节吗，写两行 if 不就行了？

可以，而且上一份发布物里就有一份“脚本动作”，本手册第 4 章还会拿它当对照组。但你会发现它很脆：换一个起始角度、地面滑一点、舵机慢一点，它就站不起来。原因是你写的其实是“一条固定轨迹”，而不是“遇到情况该怎么反应”。

**表 8  三种控制方式的取舍**

| 方法 | 需要什么 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 手工脚本 / PID | 人写的规则和参数 | 简单、可解释、无需数据 | 换场景就失效，调参靠经验 |
| 模型预测控制（MPC） | 精确的动力学模型 + 实时求解器 | 有理论保证，能处理约束 | 建模难，算力要求高 |
| 强化学习（本工程） | 仿真环境 + 奖励函数 + 算力 | 能学到人写不出的反应，泛化好 | 训练不稳定，奖励难设计 |

所以强化学习不是“更高级的控制”，而是另一条路：用大量试错换掉对精确模型的依赖。它的代价是——你得学会设计奖励、看懂训练曲线、诊断“为什么不收敛”。这正是本手册后面几章要教的东西。

### 0.4 MuJoCo 是什么，为什么选它

MuJoCo 是一个物理引擎，负责算“力作用在物体上会发生什么”：重力、碰撞、摩擦、关节约束、舵机的力矩。它只算物理，不管画面多好看。

机器人模型用 MJCF 描述——一个 XML 文件，写着有几个刚体、怎么连接、每个零件多重、关节能转多少度。第 3 章会带你逐行读完这个工程里的 MJCF。

为什么不用游戏引擎（Unity、Unreal）？因为游戏引擎优先保证“看起来真”和“跑得快”，MuJoCo 优先保证“算得准”和“稳定”。接触、摩擦这些恰恰是机器人站立的关键，算不准，学出来的策略就是错的。

### 0.5 你要解决的问题，一句话说清

机器人以四种跌倒姿态之一躺在地上（侧倒、反侧倒、前倒、后倒），策略要在 14 秒内让它站起来，并保持直立至少 1 秒。

难在三个地方：一是只有两个关节，能用的自由度极少；二是跌倒姿态不同，需要的动作完全不同；三是仿真和真机之间还有差距，学得太“死”就上不了实物。这三件事，分别对应第 3 章、第 4 章和第 7 章。

## 第 2 章 把一个仿真问题写成 MDP

这一章是全书的根。如果只能读懂一章，就读这一章。所谓 MDP（马尔可夫决策过程），听上去很学术，实际上就是回答四个问题：策略能看到什么（观测）、能做什么（动作）、做得好不好（奖励）、什么时候算结束（终止）。

### 2.1 一回合到底发生了什么

把整个训练过程想象成一场无限重复的考试，每一场（一个回合）的流程就四步：

```python
obs = env.reset()                  # 1. 把机器人摆成跌倒姿态, 返回第一帧观测
while not done:                    # 2. 一直循环到回合结束
    action = policy(obs)           #    策略看一帧, 出一个动作(10 维 -> 2 维)
    obs, reward, done, info = env.step(action)   # 3. 物理走 20 步, 返回新状态与分数
    total += reward                # 4. 把这一回合的分加起来, 就是回报(return)
```

就是这么简单。训练算法做的就是重复于万次这个过程，然后调整 policy 里面的参数，让 total 越来越大。你写代码的全部工作，就是把上面三个东西定义清楚：policy 的输入输出、env.step 里发生什么、什么时候算 done。

### 2.2 观测：给策略一双“眼睛”

观测就是策略每一步能“看到”的数字。设计观测有三条原则，违反了哪一条都会让训练变难：

- 够用：做决策真正需要的信息必须在里。少了就像蒙着眼骑车。
- 连续：相邻两帧的数值应该小幅变化。突然从 359° 跳到 1° 这种表示会误导神经网络。
- 可测：真机上能用传感器测到。仿真里偷着用了真实速度，真机上拿不到，就白训了。

本工程的 10 维观测就按这三条凑出来的：

**表 14  10 维观测逐维解释**

| 维度 | 含义 | 范围 | 为什么需要 |
| --- | --- | --- | --- |
| 0～2 | 重力方向在机体坐标系的分量 | [-1, 1] | 相当于告诉你“我歪了多少”，无万向节问题 |
| 3～4 | 两个关节当前角度 | ±1.57 rad | 知道舵机当前在哪，才能决定往哪推 |
| 5～6 | 两个关节角速度 | 不限 | 区分“静止”与“正在摆”，单帧角度看不出来 |
| 7～8 | 上一控制目标角 | ±1.55 rad | 舵机目标角是控制器的“记忆”，必须告诉策略 |
| 9 | 基座高度 | -0.1～0.5 m | 判断是贴地、坐着还是站起来了 |

#### 为什么用重力向量，而不用 roll/pitch 两个角度？

这是初学者最容易照抄而不理解的地方。roll/pitch 是欧拉角，它在“接近垂直”附近是连续的，但在“侧倒 90°”附近会跳变，而且有万向节死锁问题。更麻烦的是，它需要先做姿态解算，而真机上 IMU 拿到的原始数据就是加速度（重力方向）和角速度。

重力向量没有这些问题：站立时它接近 (0, 0, -1)，侧倒时接近 (0, -1, 0)，在整个空间里都是平滑连续的，而且和 IMU 能直接测到的量一一对应。这也是四足、人形 RL 里最通用的做法。

#### 为什么要把“上一帧动作”也放进观测？

因为舵机是位置控制的：你发的是“目标角”，它自己慢慢转过去。如果不告诉策略“我上次让它去哪”，它就不知道当前角度是“已经到位了”还是“还在路上”。把上一步动作加进来，策略才能从“现在发生了什么”推出“接下来会发生什么”。这在 RL 里叫满足马尔可夫性。

### 2.3 动作：为什么用“增量”而不是直接给角度

动作有三种常见选法，每一种都在“好不学”和“好不好用”之间做权衡：

**表 15  三种动作空间的对比**

| 方案 | 动作含义 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 力矩控制 | 直接给两个关节的力矩 | 最接近物理，上限最高 | 难训、难部署，真机需要力矩传感器 |
| 绝对角度 | 直接给目标角 | 简单直观 | 一步到位容易撞限位，探索空间大 |
| 增量角度（本工程） | 在上一目标上再转一点点 | 动作有界、平滑、易迁移 | 需要多步才能到位 |

增量形式的具体公式是：新目标 = 旧目标 + 0.08 × 动作，然后再限幅到 ±1.55 rad。其中 0.08 是每个控制步（20 毫秒）最多能转的弧度，相当于大约 4.6 度。

选它的理由很实际：一是动作幅度天然有界，神经网络不会输出“转 500 度”这种荒唐值；二是策略只需学“往哪个方向推、推多快”；三是这个接口与真机的位置舵机、遥控手柄都能对上，部署时不用改代码。

### 2.4 奖励：把你的愿望翻译成分数

奖励是整个实验里最值得反复改的部分。先讲一个概念：稀疏奖励与稠密奖励。

稀疏奖励就是“只有成功才给分”。好处是目标明确，坏处是太难学——机器人随机探索一万次都没成功一次，就学不到任何东西，就像考试只告诉你“错了”却不告诉你错在哪里。

稠密奖励是“每一步都给点提示”。比如“比刚才更直一点就加分”。它的代价是你得小心：策略会专找能拿分却不干活的捷径，这就是所谓的奖励作弊。

**表 16  本工程的五项奖励**

| 项 | 权重 | 它在鼓励什么 | 可能被怎么作弊 |
| --- | --- | --- | --- |
| upright | +1.0 | 身体越接近竖直分越高 | 快速抖动也能瞬时站直 |
| height | -0.5 | 偏离 0.08 m 就扣分 | 可能让策略不敢动 |
| progress | +0.2 | 比上一步更直才加分 | 贴近基线时反复微调刷分 |
| action_rate | -0.02 | 惩罚动作突变 | 会让策略变得迟铝、反应慢 |
| joint_vel | -0.001 | 惩罚关节甩动 | 可能“站不起来但也不抖” |
| success / fail | +10 / -5 | 只在结束时给 | 无（就是终端信号） |

一个真实的例子：如果只给 upright，你会看到一个“高频抖动”的策略——它在每一帧都把基座抽到竖直，但根本站不住。upright 曲线很好看，成功率却接近 0。这时候应该看的是 action_rate 惩罚和“保持 1 秒”的成功判定，而不是继续调学习率。

#### 四条奖励设计经验

1. 每一项都要能回答“它在防什么作弊”。答不出来的项，先删掉。
2. 先用 2～3 项跑通，再加。一次写十几项，出事了你不知道是哪一项捣的鬼。
3. 终端奖励要明显大于单步奖励。否则策略会觉得“反正每步都能拿分，成功不成功无所谓”。
4. 惩罚要有度。把所有惩罚调很大，策略会学成“原地不动最安全”。

### 2.5 终止条件：什么时候算一回合结束

**表 17  终止条件与依据**

| 条件 | 阈值 | 为什么要这样定 |
| --- | --- | --- |
| 成功 | 倾角 ≤ 14.32° 且保持 1.0 s | “一瞬间直立”不算站住，保持一秒才排除运气 |
| 超时 | 单回合 14 s | 参考工程的实际节奏，太短学不会，太长浪费时间 |
| 失败 | 高度 < -0.05 m 或数值发散 | 防守性保护，避免把仿真跑飞 |

这里最值得学的是“保持 1 秒”这个设计。它把“短暂直立”和“真的站稳”区分开了，也是防止策略刷分最有效的一招。你以后自己设计任务时，这个技巧可以直接拿来用。

## 第 3 章 读懂模型：一个 MJCF 文件

assets/robo1.xml 一共九十几行。它不是“配置文件”，而是这个机器人的全部物理定义：几个刚体、怎么连、多重、关节能转多少、舵机多大劲。这一章带你逐段读完它。

### 3.1 先看一眼骨架

把 XML 展开，其实就是六个块，顺序固定：

```xml
<mujoco model="robo1">
  <compiler .../>      <!-- 单位、网格目录 -->
  <option .../>        <!-- 时间步长、重力、积分器 -->
  <asset> ... </asset>  <!-- 6 个 STL 网格 -->
  <default> ... </default>  <!-- 关节与执行器的默认参数 -->
  <worldbody> ... </worldbody>  <!-- 刚体树 -->
  <actuator> ... </actuator>  <!-- 两个位置舵机 -->
```

记住这个骨架，以后换任何机器人模型都是这六个块。

### 3.2 六个块分别在说什么

**表 19  MJCF 各块的作用**

| 块 | 作用 | 本工程的取值 | 改它会怎样 |
| --- | --- | --- | --- |
| compiler | 单位、网格路径、自动限位 | angle=radian, meshdir=meshes | 写错就加载不了网格 |
| option | 时间步长、重力、积分器 | timestep=0.001, implicitfast | 影响稳定性和速度 |
| asset | 声明网格文件 | 6 个 STL | 漏一个就报错 |
| default | 批量默认值 | 关节限位 ±1.5708；舵机 kp=0.5、kv=0.04 | 改了所有关节/执行器一起变 |
| worldbody | 刚体与关节的树 | foot 带 free joint，arm1/arm2 各带一个 hinge | 改结构或质量 |
| actuator | 驱动关节的执行器 | 2 个 position 舵机 | 改控制方式 |

### 3.3 这棵树长什么样

世界坐标系下先是一块地面（plane），然后是机器人本体。刚体是嵌套的，像搭积木：

```text
worldbody
```

└─ foot（底座，带 free joint：可以自由平移旋转，所以会倒）

├─ ATOM（主板模型，纯展示，无独立自由度）

├─ servo1（下舵机外壳）

└─ arm1（下连杆，带 hinge：只能绕 x 轴转）

├─ servo2（上舵机外壳）

└─ arm2（上连杆，带 hinge：只能绕 y 轴转）

这里有两个关键点。第一，只有 foot 挂的是 free joint，它决定了整台机器人能不能倒、能不能在平面上滑。第二，两个 hinge 都限位在 ±1.5708 rad（也就是 ±90°），超出就会被物理上挡住。

每个 body 里还有一段 <inertial>：这就是质量与转动惯量。它们是从 CAD 里算出来的，决定了“推一下有多难”。初学者常见错误是随手填个 mass=1，结果机器人重得站不起来。

### 3.4 维度是怎么算出来的

**表 20  三个数组的维度**

| 数组 | 维度 | 怎么算的 | 里面是什么 |
| --- | --- | --- | --- |
| qpos | 9 | free joint 3（位置）+ 4（四元数）+ 2 个 hinge | 机器人的完整位姿 |
| qvel | 8 | free joint 6（三平移 + 三旋转）+ 2 个 hinge | 每个自由度上的速度 |
| ctrl | 2 | 两个 position 执行器 | 两个舵机的目标角 |

9 和 8 不相等，很多初学者会吓一跳。原因是位置用四元数（4 个数）表示姿态，而速度用三轴角速度（3 个数）表示旋转——信息量一样，编码方式不同。

自己验证一下（在工程根目录）：

```python
import mujoco
m = mujoco.MjModel.from_xml_path("assets/robo1.xml")
print(m.nq, m.nv, m.nu, m.opt.timestep)
print(m.jnt_qposadr, m.jnt_dofadr)
```

应该看到 9 8 2 0.001，以及 qpos 地址 0/7/8、dof 地址 0/6/7。这两个地址表告诉你：第 0～6 位是基座，第 7、8 位是两个关节。这就是 env.py 里索引的依据。

### 3.5 为什么执行器用 position

XML 里的舵机是这样声明的：

```xml
<position name="servo1_pos" joint="servo1_joint"
          ctrllimited="true" ctrlrange="-1.5708 1.5708"
          forcelimited="true" forcerange="-1.0 1.0"
          kp="0.5" kv="0.04"/>
```

position 执行器做的事是：拿目标角和当前角的差，乘上 kp 得到“想使多大劲”，再乘上 kv 抑制振荡，最后把力矩限制在 forcerange 里。这就是真实舵机内部的伺服环。

为什么不用力矩控制？因为力矩控制在仿真里更“干净”，但上真机时你会同时面对模型误差、电流限制、舵机死区和通信延迟。对第一个 sim2real 项目，位置接口的迁移成本低得多——这也是原工程的选择。

### 3.6 三个动手实验：改一个数，看它怎么变

读十遗不如改一次。下面三个实验都在 robo1.xml 里改一个数，改完跑 python -m scripts.selftest 或 run_scripted 看变化。改之前先备份。

#### 实验一：把 timestep 从 0.001 改成 0.002

预期：仿真变快一倍，但接触开始抖，机器人容易穿地面或弹飞。原因：步长变大，积分精度下降。注意 env.py 会自动把 frame_skip 从 20 算成 10，保持 50 Hz，所以控制频率不变，变的只是物理精度。

#### 实验二：把 kp 从 0.5 改成 2.0（再试 0.1）

预期：kp 变大，舵机变“硬”，动作更快但容易振荡；kp 变小，舵机变“软”，可能根本撑不起体重。这说明一个道理：执行器参数本身就是 sim2real 的一部分，真机上的 MG90S 与你填的 kp 不会完全一致。

#### 实验三：把 forcerange 从 ±1.0 改成 ±0.2

预期：成功率大幅下降甚至归零。原因：力矩不够，做不到需要的动作。这也是一个很真实的工程约束——小舵机的扭矩永远是不够的。

### 3.7 一个必须知道的碰撞细节

原模型里所有名为 *_collision 的盒子都写着 contype="0" conaffinity="0"。在 MuJoCo 里，这两个数字是“碰撞分组掩码”，写成 0 就等于“我不参与任何碰撞”。

结果是：真正在碰地面的是 STL 网格的凸包，而不是那些规规矩矩的盒子。凸包接触在外形上还算可用，但底部平面会被近似，接触点偏“虚”，直接导致学出来的策略“仿真里能站、实物上抖”。

修正方法很简单：把盒子的 contype、conaffinity 删掉（恢复默认 1），把网格 geom 加上 contype="0" conaffinity="0"。改完用同一份配置重训一次，对比成功率与“站直后是否抖动”。具体操作在第 5.7 节。

第一次改模型建议只改这一处，不要同时改好几个参数。否则出问题时你分不清是哪一处引起的。

## 第 4 章 第一个实验：先看对照组

在碰任何学习算法之前，先把“不学习”的水平测出来。这个数字后面会一直用到：它就是 RL 要超越的基线。

### 4.1 跑起来

```bash
python -m scripts.run_scripted --episodes 5
```

它会按 reference/reference-learning.json 里的关键帧，把关节目标角按时间轴播一遍。注意它是开环的：不看你当前是什么姿态，只是一味地“按剧本演”。

### 4.2 报表怎么看

**表 21  基线报表的四个列**

| 列 | 含义 | 怎么判读 |
| --- | --- | --- |
| 成功率 | 该姿态下站起来的回合占比 | 这是 RL 要超越的基线 |
| 平均回报 | 按奖励函数算的回合总回报 | 与成功率一起看，防止奖励与目标脱钩 |
| 平均用时 | 从开局到站直并保持 1 秒 | 3 秒以内算干净 |
| 最差姿态 | 四个姿态里成功率最低的 | 比平均值更能说明问题 |

为什么要按姿态分开看？因为“平均 75%”这种数字会骗人——可能是三个姿态都会、一个完全不会。按姿态拆开才能看出策略是不是只学会了某一个方向。

### 4.3 基线不成功怎么办

- 机器人完全不动：检查执行器有没有收到 ctrl，或者关节是不是被 default 里的限位锁死。
- 机器人在动，但方向反了：参考动作是在不同模型版本上录的，符号约定可能不一致；把 targets 整体取反再试。
- 动到一半飞出去：积分器或碰撞参数有问题，先回自检看数值是否发散。

记住一个判断：如果脚本基线四个姿态全失败，RL 也几乎不可能成功。这时候应该去查数据和模型，而不是调超参。

### 4.4 基线给你的三个信息

1. 任务难不难：如果脚本都站不起来，说明物理或参考动作有问题。
2. 哪些姿态难：pitch 方向需要更大行程，通常比 roll 方向难。
3. 目标定在哪：RL 超过基线多少，才算真的学到了东西。

## 第 5 章 第二个实验：训练 PPO

这一章最长，但也是你最想学的部分。先花三分钟把 PPO 在做什么搞清楚，再动手。

### 5.1 PPO 到底在做什么

用一个比喻：你在蒙着眼调一个老旧收音机的旋钮，目标是把声音调到最清楚。你看不见旋钮在哪，只能拧一下、听一下。拧对了就继续，拧错了就退回来。PPO 就是一套“怎么拧”的规矩。

具体到机器人：策略网络就是一个旋钮很多的收音机（这里是几万个参数），观测是眼睛，动作是声音。训练就是反复：“跑一遍看看得多少分 → 哪个动作比平均好 → 把那个动作的概率调大一点”。

PPO 的三个关键词，理解了它们就读懂了训练曲线：

- 优势（advantage）：这个动作比“平均水平”好多少。比平均好，就多鼓励。
- 剪切（clip）：每次只允许策略改一点点，防止一步改崩。这是 PPO 名字的来源。
- 熵（entropy）：保持一点随机性。熵太低，策略会过早“认死理”，卡在局部最优。

### 5.2 一次训练里循环发生的五件事

**表 22  PPO 训练循环**

| 步骤 | 做什么 | 对应代码 |
| --- | --- | --- |
| 1 采样 | N 个环境并行跑，收集（观测, 动作, 奖励） | SubprocVecEnv + env.step |
| 2 估分 | 用价值网络估计每个状态值多少分 | PPO 内部 Critic |
| 3 算优势 | 实际回报减去估计值，得到优势 | GAE（gamma/lambda） |
| 4 更新 | 把好动作的概率调大，clip 限制幅度 | PPO 内部 Actor |
| 5 评估 | 每 2 万步跑一次四个姿态，算成功率 | PoseEvalCallback |

每次循环的“数据量”就是 n_envs × n_steps。比如 8 个环境 × 48 步，一轮就有 384 个样本。总共跑 30 万步，大约就是 780 轮。

### 5.3 跑起来

```bash
python -m scripts.train_ppo --config configs/ppo_fast.json
```

这套配置是 8 个并行环境、总共 30 万步。在 4 核 CPU 上大约十几到二十几分钟。它的目的不是“训出最好的模型”，而是让你在半小时内把整条流程跑通。

训练中每 2 万步会自动评测一次，打印类似这样一行：

```text
[eval] step= 20000 success= 12.5% worst= 0.0% roll_pos=0% roll_neg=50% ...
```

早期成功率低是正常的。关键看趋势：它是否在往上走，以及是不是只学了某一个姿态。

## 第 6 章 第三个实验：三组消融

跑一次成功的训练只能证明“这条路能走通”。做三组对照才能告诉你“哪一部分真的起作用”。这也是一门课里最能拉开差距的练习。

### 6.1 消融的规矩：一次只改一个变量

消融（ablation）原本是医学词，意思是“拿掉某个部分，看功能会不会消失”。在 RL 里就是：保持其他全部不变，只去掉或改掉其中一个设计，看指标怎么变。

两条铁律：一次只改一处；同一组对比必须用同一个 seed。违反了哪一条，结论就不成立。

### 6.2 三组实验的具体改法

#### 实验 A：拿掉 progress 项

打开 selfrising/reward.py，把 w_progress 从 0.2 改成 0.0，重训 ppo_fast。你会看到：成功率可能略降，但动作变平滑了。

为什么值得做？因为 progress 是典型的“稠密信号”，它帮助策略在早期就知道“往哪个方向推”。去掉它，就等于把稠密奖励变回稀疏奖励，能直接看到探索变慢。

#### 实验 B：把观测换成欧拉角

打开 selfrising/env.py 里的 _obs()，把前三行（重力向量）换成 roll/pitch，加一个常数占位。具体代码：

```python
gx, gy, gz = g_b
roll = np.arctan2(gy, -gz)
pitch = np.arctan2(-gx, np.hypot(gy, gz))
obs = np.concatenate(([roll, pitch, 0.0], q, dq, self.target, [height]))
```

这样观测维度还是 10 维，对比才公平。观察结果：也许变好，也许变差。如果变差，你就亲眼看到了“表示形式也能影响学习效率”；如果变好，也不要惊讶——在小状态空间里欧拉角未必输。

#### 实验 C：加一步动作延迟

在 configs/ppo_fast.json 的 env 里把 action_delay 改成 1，重训。这是三项实验里最接近真实部署的一项。

预期：成功率下降，但策略动作变得更保守、更平滑。这正是真机需要的——真机上从决策到舵机到位，总会有十几到几十毫秒的延迟。

### 6.4 结论怎么写

不要写“效果变差了”这种话。用“现象 → 解释 → 下一步”三段式：

现象：A 组总体成功率从 78% 降到 61%，降幅集中在 pitch 方向（pitch_pos 由 80% 降到 20%）。

解释：progress 提供稠密信号；去掉后，需要更大行程的 pitch 方向探索不足。下一步：把 w_progress 调到 0.1 做中间值对比，或引入课程学习。

### 6.5 三个统计陷阱

- 只看一个 seed。不同 seed 的成功率可能差二三十个百分点。至少跑 2～3 个 seed 看方差。
- 只看平均值。一个姿态 0%、其他三个 90%，平均也是 67%，但机器人实际上一半场景用不了。
- 只看最好的一次。训练后期可能回落，best_model 才是你要评的那个。

## 第 7 章 第四个实验：从仿真走向实物

这一章不一定需要你有真机。即使只在仿真里做，你也能学到 sim2real 的思维方式：先搞清楚“仿真和真机到底差在哪”，再决定怎么补。

### 7.1 仿真与真机的三个差距

**表 28  三类不确定性**

| 差距 | 具体表现 | 在仿真里怎么模拟 |
| --- | --- | --- |
| 模型参数 | 零件质量、重心、摩擦系数与实测不一致 | 域随机化：每回合随机缩放 |
| 执行器 | 舵机有死区、延迟、力矩不如标称 | 动作延迟 + 增益扰动 |
| 感知 | IMU 有噪声、有零漂、采样率有限 | 观测噪声 |

初学者常犯的错：在仿真里追求 99% 成功率。那是“应试”，真机上反而容易崩。正确的目标是：在扰动下仍然有 70～80% 成功率，而且失败时不会抖动。

### 7.2 三项随机化

**表 29  ppo_robust 里的三项随机化**

| 随机化 | 仿真里怎么模拟 | 真机上对应什么 |
| --- | --- | --- |
| 动作延迟 1 步 | 动作队列滞后 20 ms | 无线/总线通信与舵机响应 |

### 7.4 上实机的六个步骤

1. 标定：让两个舵机在同一目标角下保持机械对称，记下中位与行程。
2. 录观测：静止、手动推倒，把 IMU 读数与仿真里的重力向量对一遍，确认符号。
3. 限幅：把动作增量先砍一半跑，确认不撞限位，再恢复。
4. 低速试跑：用 --slowdown 或降低控制频率，看动作是不是你想要的那个方向。
5. 逐步放开：先 roll 方向、再 pitch 方向；先硬地、再地毯。
6. 记失败：每次失败记下姿态、地面、电量。这些记录比任何调参都值钱。

#### 四步路线：导出 → 生成头文件 → 写循环 → 标定

跟 A 工程的做法一致：把训练好的网络权重导成 C 数组，写进一个头文件，固件里直接做前向。比在单片机上跑 ONNX 简单得多，也快得多。

不用从零开始建：工程里已经放了一份可直接编译的骨架 firmware/（platformio.ini、main.cpp、policy_runtime.h、tools/export_policy.py）。下面的三段文字与这四个文件一一对应，你可以边读边对照。

第一步，打开 firmware/ 里的 platformio.ini（或按下面的样子新建一个）：

```ini
[env:esp32dev]   ; 一个配置文件管依赖、编译与烧录
platform = espressif32
board = esp32dev
framework = arduino
lib_deps =
    adafruit/Adafruit BNO055 @ ^1.6.3
    madhephaestus/ESP32Servo @ ^3.0.0
```

第二步，写控制循环。骨架长这样，核心就三件事：固定 50 Hz、拼出 10 维观测、把动作累加到目标角：

```cpp
#include <Arduino.h>
#include "policy.h"   // 训练端导出的权重
const uint32_t PERIOD_US = 20000;   // 50 Hz
float target[NUM_JOINTS] = {0.0f, 0.0f};
void loop() {
  static uint32_t last = 0;
  if (micros() - last < PERIOD_US) return;
  last = micros();
  float obs[OBS_DIM], act[ACT_DIM];
  read_observation(obs);        // 重力向量 + 关节角 + 上一步目标
  policy_forward(obs, act);     // 10 -> 64 -> 64 -> 2
  for (int i = 0; i < 2; ++i)
    target[i] = constrain(target[i] + 0.08f * act[i], -1.55f, 1.55f);
  servo_write(target);          // 弧度 -> 脉宽
}
```

你只要保证三件事与仿真一致：观测的顺序与归一化、动作的缩放系数 0.08、限幅 ±1.55。任何一项不同，策略都会立刻失效——这也是第 7.3 节那张对齐表存在的理由。

第三步，导权重。把训练好的网络每一层的矩阵与偏置打印成 C 数组，写进 policy.h。网上有很多“PyTorch 权重转 C 数组”的小脚本，核心就是把 state_dict 里的张量按行展开。

第四步，标定。先空载测试两个舵机的中位、方向与行程，把软件里的弧度与真实脉宽对一遭；再限制目标角的变化率，避免第一次上电就撞限位。

#### 为什么不直接上 ONNX

ESP32 上跑 ONNX 需要额外的运行时（占内存、配置麻烦，还要处理算子兼容）。对一个 10 进 2 出、两层 64 宽的小网络，手写前向只有几十行，反而更快、更好调、更容易看懂。ONNX 的价值在 PC 端做验证与交换，不是必须上单片机。

如果你想少走弯路：先用原发布物的预编译固件和网页安装器把动作看到，再回来自己在 PlatformIO 里复现。先看到效果，再理解原理，比一上来就搭工程更容易坚持。

### 8.3 一个通用的调试方法

当你想不明白的时候，把问题缩到最小：

1. 先只跑一个环境（--n-envs 1），排除并行带来的不确定性。
2. 先把回合缩短（把 14 秒改成 3 秒），看能不能跑完。
3. 先用零动作跑一回合，确认环境本身不会飞。
4. 先用脚本策略跑，确认接口能打通，再换学习策略。

这四步的本质是“分段验证”：把一条长链拆成几段，一段一段确认。这是比问人更快的方法。

## 附录 E 自测题答案

答案只给要点，不是标准答案。你的表述与这里不同但意思对，就是对的。

1. 仿真一步毫秒级、无硬件损耗、可重复；代价是仿真与真实的差距。
2. 观测=能看到的信息；动作=能做的事；奖励=每步分数；策略=观测到动作的函数；回合=一次完整尝试。
3. PID 靠人写规则和参数，RL 靠数据与试错；RL 不需要精确模型，但需要大量采样。
4. 算刚体动力学、接触与摩擦；游戏引擎优先视觉与速度，接触精度不够。
5. qpos = 3 位置 + 4 四元数 + 2 关节 = 9；qvel = 3 平移 + 3 旋转 + 2 = 8。
6. 1 ms 决策会让 14 s 变成 14000 步，成本高一个数量级；真机舵机信号也在 50 Hz 量级。
7. kp 是拉向目标的刚度，kv 是阻尼；两者一起决定“多硬、多不抖”。
8. 不参与任何碰撞；实际碰撞由 STL 凸包承担，接触不准，导致仿真能站、实物抖。
9. 欧拉角在跳变处不连续、有万向节问题，且需姿态解算；重力向量连续且 IMU 直接可测。
10. 舵机是位置控制，目标角是控制器的记忆；不给就分不清“已到位”和“还在路上”。
11. 动作有界、平滑、易迁移；绝对角度一步到位易撞限位、探索空间大。
12. 稀疏：目标明确但难探索；稠密：好学好训但容易被作弊。
13. 区分“瞬时直立”与“真的站稳”，防止刷分。
14. 说明任务难度、哪些姿态难、RL 要超过多少。
15. 限制每次策略更新幅度；太死学得极慢，太松会崩。
16. 奖励与目标脱钩，策略在做能拿分却不解决问题的行为。
17. 防止过拟合到评测姿势，并能看出方差。
18. 否则分不清结果变化是哪一个改动引起的。
19. 为了在参数、延迟、噪声不确定时仍能工作，提升实际上机成功率。
20. 控制频率、姿态观测（重力向量）、关节目标与限幅。
